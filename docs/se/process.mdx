# Software Process

Process used in software industry to design, develop, test, and deliver software.

## Requirements Analysis

**Inputs**:
- Meeting notes, stakeholder input documents (stakeholder interviews, user research)
- Requirements specifications, backlog items (workshops, brainstorming)
- Market research reports, customer insights (market research)
- Prioritized backlog, feature breakdowns (backlog grooming)
- ...

**Process**:
- Create a Project Overview Document to capture scope, objectives, and context 
- For each proposed feature, create a detailed Feature Specification Document

**Outputs**:
- [Project Overview Document](./process/project-overview.mdx)
- [Feature Specification Document](./process/requirements/fsd.mdx) (FSD)

:::note
Each FSD defines a single feature. FSDs are grouped into modules.
:::

:::info
A **module** (e.g., user management, payment processing) represents a collection of related features.  
A **feature** is the smallest unit of work that can be implemented and delivered independently.
:::


## Design

Translate feature requirements into a precise technical blueprint that engineers can implement.

### User Interface

**Inputs**:
- The feature to be implemented
- The Feature Specification Document for that feature

**Process**:
1. Identify all required screens based on the Feature Specification Document
2. For each screen, create a dedicated UI Design Document

**Outputs**:
- [UI Specification Documents](./process/design/ui-spec.mdx) for all screens of the feature

:::note
Each UI Specification Document defines a single screen. Like FSDs, they are organized into modules.
:::

### API

**Inputs**:
- The feature to be implemented  
- UI Specification Documents for the feature

**Process**:
1. From each UI Specification Document, identify required APIs  
2. For each API, create an API Specification Document

**Outputs**:
- [API Specification Documents](./process/design/api-spec.mdx) for all APIs of the feature

:::note
Each API Specification Document defines a single API. Like FSDs, they are organized into modules.
:::

### Data Model

**Inputs**:
- API Specification Documents of a module

**Process**:
1. Identify all entities referenced in the module's APIs
2. Define attributes and their constraints for each entity
3. Define relationships between those entities 

**Outputs**:
- [Data Model Document](./process/design/dmd.mdx)

:::note
Each module has one Data Model Document describing all its entities and their relationships.
:::

### System Architecture

**Inputs**:
- The feature to be implemented  
- Feature Specification Document
- API Specification Documents for the feature

**Process**: see [System Design Process](./system-design.mdx#system-design-process) section.

**Outputs**:
- [Architecture Overview Document](./process/design/arch-overview.mdx)
- [Component Design Documents](./process/design/comp-design.mdx)


## Implementation

**Inputs**:
- The feature to implement
- Feature Specification Document
- UI Specification Documents (for frontend implementation)
- API Specification Documents, Data Model Document, System Architecture Document(for backend implementation)
- Repository Structure Document (how the code base is organized)
- Coding standards (rules for writing code)
- Coding recipes (code snippets for common tasks)

**Outputs**:
- Application's source code
- Setup instructions for source code


## Testing

**Outputs**:
- Test Suite document
- Test code (Unit tests, Integration tests, End-to-end tests, etc.)


## Deployment

**Outputs**:
- Runtime environments: staging, production, etc.
- Deployment Guides
- Infrastructure code (IaC) or Deployment scripts
- CI/CD pipelines configuration
