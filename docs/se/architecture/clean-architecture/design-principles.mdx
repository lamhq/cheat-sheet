# Design Principles

## Introduction

Design principles are general guidelines for arranging code into structures that are easy to change, easy to understand, and reusable. They work at the module/class level, just above individual lines of code.

The Clean Architecture is built around five object-oriented design principles (SOLID):

| Principle | Meaning                         | Main objective                              |
| --------- | ------------------------------- | ------------------------------------------- |
| SRP       | Single Responsibility Principle | One reason to change                        |
| OCP       | Open-Closed Principle           | Open for extension, closed for modification |
| LSP       | Liskov Substitution Principle   | Subtypes should be substitutable            |
| ISP       | Interface Segregation Principle | Prefer small, focused interfaces            |
| DIP       | Dependency Inversion Principle  | Depend on abstractions                      |


## Single Responsibility Principle (SRP)

**A module should be responsible to one, and only one, actor**.

**Bad** example:

```ts
class Employee {
  calculateSalary(): void {}
  generateReport(): void {}
  saveToDatabase(): void {}
}
```

This class combines responsibilities associated with different actors.

**Better**:

```ts
class SalaryCalculator {
  calculateSalary(): void {}
}

class EmployeeReport {
  generateReport(): void {}
}

class EmployeeRepository {
  save(): void {}
}
```

**Key idea**: Separate responsibilities that change for different reasons.

## Open-Closed Principle (OCP)

Software entities should be open for extension but closed for modification.

**Bad** example:

```ts
class PaymentService {
  pay(type: string, amount: number): void {
    if (type === "CREDIT_CARD") {
      // Credit card payment
    } else if (type === "PAYPAL") {
      // PayPal payment
    }
  }
}
```

Every new payment method requires modifying the existing class.

**Better**:

```ts
interface PaymentMethod {
  pay(amount: number): void;
}

class CreditCardPayment implements PaymentMethod {
  pay(amount: number): void {}
}

class PaypalPayment implements PaymentMethod {
  pay(amount: number): void {}
}
```

Now new payment methods can be added without changing the core payment service.

## Liskov Substitution Principle (LSP)

Objects of a subtype should be usable wherever objects of their base type are expected without breaking correctness.

For example, if a function expects a `PaymentMethod`, every implementation must honor the expected payment contract.

A subtype should not:

- Unexpectedly reject valid inputs.
- Weaken guarantees.
- Introduce unexpected behavior.

## Interface Segregation Principle (ISP)

Clients should not depend on methods they do not use.

**Bad**:

```ts
interface Machine {
  print(): void;
  scan(): void;
  fax(): void;
}
```

A printer that cannot scan or fax is forced to implement irrelevant methods.

**Better**:

```ts
interface Printer {
  print(): void;
}

interface Scanner {
  scan(): void;
}

interface Fax {
  fax(): void;
}
```

## Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions.

**Bad**:

```ts
class OrderService {
  private readonly repository: MySQLOrderRepository =
    new MySQLOrderRepository();
}
```

The business logic directly depends on MySQL implementation.

**Better**:

```ts
interface OrderRepository {
  save(order: Order): void;
}

class OrderService {
  constructor(private readonly repository: OrderRepository) {}
}
```

Now the application can use MySQL, PostgreSQL, MongoDB, or an in-memory implementation without changing `OrderService`.
